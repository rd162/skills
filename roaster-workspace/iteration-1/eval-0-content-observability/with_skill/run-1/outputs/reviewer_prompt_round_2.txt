The first time observability earned its keep for me, it was 2 a.m. and a dashboard was lying to me.

Every metric was green. CPU fine, memory fine, error rate flat. And yet a handful of customers couldn't check out. The dashboards covered every failure we'd already thought of — and this wasn't one of them.

That gap is the whole difference between monitoring and observability, and it's worth being precise about because the two get used as synonyms.

Monitoring answers questions you knew to ask in advance. You decide up front what matters — request rate, p99 latency, queue depth — and you build dashboards and alerts for those. It's great at catching the failure modes you've already seen.

Observability is about the failures you haven't seen. It's the ability to ask a brand-new question of your running system — one nobody built a dashboard for — and actually get an answer, without shipping new code to add the instrumentation.

The 2 a.m. incident is a good example. The fix wasn't another dashboard. It was being able to take the raw request data and slice it by fields we'd never pre-aggregated: group the failures by customer ID, then by payment provider, then by app version. Thirty seconds later the shape was obvious — one provider was timing out, but only for customers on a build we'd shipped that afternoon. No pre-built chart would have shown that, because we didn't know to build it.

That's the practical test I now use: if answering "why is this broken?" requires you to ship a code change first to add the metric, you have monitoring, not observability. The cost of that distinction is real — high-cardinality data (anything you'd want to group by user, build, or region) is genuinely expensive to store and query, and pretending otherwise is how teams end up with surprise bills.

It does pay off, but slowly, not overnight. In New Relic's 2025 Observability Forecast, teams with full-stack observability were far less likely to hit frequent high-impact outages — 23% of them versus 40% of teams without it. Worth noting that those are teams that have invested for a while; the survey's "leaders" are the ones with years of maturity behind them, not a tool they switched on last week.

So I'd retire the line that observability is "a mindset" or "the future." It's a concrete capability: can you interrogate your system about a problem you didn't predict? If a recent incident took you hours because the data existed but you couldn't slice it the way you needed, that's the gap worth closing first.
