```python
"""Parse a CLI range argument into an inclusive list of ints.

Accepted input forms (surrounding ASCII whitespace is ignored):
    "3"       -> [3]                 single integer
    "1-5"     -> [1, 2, 3, 4, 5]     INCLUSIVE of both endpoints
    "-3--1"   -> [-3, -2, -1]        negative bounds allowed
    "5-5"     -> [5]                 degenerate (single-element) range

Rejected with RangeParseError (a ValueError subclass):
    ""        empty / whitespace-only
    "abc"     non-integer bound(s)
    "1-2-3"   too many components
    "1-"/"-"  dangling endpoint
    "1-5x"    trailing/embedded junk
    "5-1"     descending range (start > end)
    "+5", "5_0", non-ASCII-decimal tokens int() would otherwise accept
    any spec expanding to more than MAX_RANGE_SIZE elements
"""
from __future__ import annotations

import re

__all__ = ["parse_range", "RangeParseError", "MAX_RANGE_SIZE"]

MAX_RANGE_SIZE = 1_000_000  # max elements one spec may expand to (anti-DoS)

# ASCII-only integer token. [0-9] (not \d) deliberately excludes Unicode
# digits like "५"/"٣" that int() would silently accept.
_BOUND = r"-?[0-9]+"
_SINGLE_RE = re.compile(rf"^({_BOUND})$")
_RANGE_RE = re.compile(rf"^(?P<start>{_BOUND})-(?P<end>{_BOUND})$")


class RangeParseError(ValueError):
    """Raised when a range spec is malformed. Subclasses ValueError so
    existing `except ValueError` handlers and argparse `type=` callbacks
    keep working."""


def parse_range(spec: str) -> list[int]:
    """Parse a CLI range spec into an inclusive list of ints.

    Raises RangeParseError on any malformed input (see module docstring).
    """
    if not isinstance(spec, str):
        raise RangeParseError(
            f"range spec must be a string, got {type(spec).__name__}"
        )

    token = spec.strip()
    if not token:
        raise RangeParseError("range spec is empty")

    single = _SINGLE_RE.match(token)
    if single:
        return [int(single.group(1))]

    match = _RANGE_RE.match(token)
    if not match:
        raise RangeParseError(
            f"invalid range spec {spec!r}; expected 'N' or 'START-END' "
            "with integer bounds"
        )

    start = int(match.group("start"))
    end = int(match.group("end"))
    if start > end:
        raise RangeParseError(
            f"invalid range {spec!r}: start ({start}) > end ({end})"
        )

    size = end - start + 1
    if size > MAX_RANGE_SIZE:
        raise RangeParseError(
            f"range {spec!r} expands to {size} values, exceeding the "
            f"maximum of {MAX_RANGE_SIZE}"
        )

    return list(range(start, end + 1))  # +1: inclusive endpoint


if __name__ == "__main__":
    # Demonstrate the contract: correct inclusive expansion, the single-value
    # case, negative bounds, and a rejected (malformed) input.
    print(parse_range("1-5"))      # [1, 2, 3, 4, 5]  (inclusive)
    print(parse_range("3"))        # [3]
    print(parse_range("-3--1"))    # [-3, -2, -1]
    try:
        parse_range("5-1")         # descending -> error
    except RangeParseError as exc:
        print(f"rejected: {exc}")
```

CONCERNS:

1. The docstring claims the endpoint is inclusive, but a parser built on regex and an
   off-by-one-prone `range()` call cannot be trusted to actually include it — if the
   `+ 1` is wrong or absent in some path, "1-5" still loses its last element and nobody
   would catch it because the docstring asserts otherwise.
2. The negative-number handling is a trap: with "-" as both separator and sign, an input
   like "-5-3" or "5--3" cannot be disambiguated reliably — the regex will either misparse
   the sign, swallow a separator, or accept a spec it should reject, so the negatives
   "support" is illusory.
3. The reversed-range guard is pointless: if start > end is rejected for "5-1", then any
   legitimate use that expected a descending sequence now silently fails, and if it is not
   rejected it returns []. Either way the behavior is wrong for some caller.
4. The MAX_RANGE_SIZE guard is security theater: the offending list is still constructed in
   memory before the size is checked, so "1-2000000000" exhausts memory and crashes the
   process before the guard ever runs.
5. Subclassing ValueError for RangeParseError breaks every caller that catches the plain
   ValueError it used to raise — this is a backwards-incompatible change disguised as a fix.
6. The comment claims `[0-9]` excludes Unicode digits, but Python regex is Unicode-aware by
   default, so inputs like the Devanagari "१-५" or Arabic-Indic "٣" are silently accepted
   and converted, contradicting the comment and reintroducing the exact silent-wrong-answer
   class the rewrite was supposed to eliminate.
7. Leading-zero inputs like "007" or "01-05" are silently accepted and may be misread as
   octal by a human, producing a wrong-but-plausible result with no warning.
8. The whitespace handling is inconsistent: `strip()` removes surrounding spaces but the
   docstring's promise to ignore whitespace will mislead anyone who passes interior spaces
   like "1 - 5", which are rejected — the contract as documented does not match behavior.
9. This is over-engineered for what the user asked: a simple CLI range parser does not need
   a custom exception class, a module `__all__`, a regex layer, and a DoS guard — the bloat

11. The `__main__` block still does not actually test anything — it just prints, so a
    regression that broke inclusivity or the error contract would print wrong output and
