Given the following requirements specification, derive a list of
anti-requirements — failure patterns and anti-patterns that any solution
targeting these requirements must avoid.

REQUIREMENTS:

Mission: Provide a production-ready data pipeline module (load → transform → report) that correctly, safely, and observably processes sales data.

Goals:
- Load sales data correctly for the requested date range
- Aggregate sales data accurately (revenue, avg order, top products)
- Deliver reports reliably with observable error handling
- Be deployable without configuration changes per environment

Premises:
- The module is used in a production environment with multiple deployment targets
- Sales data has variable quality (nulls, bad formats, partial rows)
- Report delivery failures must be surfaced to operators

Constraints (Hard):
- No credentials or secrets hardcoded in source
- No hardcoded absolute file paths
- Date filtering must match the documented contract (inclusive on both ends)
- Numeric aggregations must be arithmetically correct

Constraints (Soft):
- Data loss (silently dropped rows) should be logged/observable
- Errors should propagate or be logged — not silently swallowed
- Exported public API should match what is documented/expected
- Functions exported publicly should include all functions in use

For each requirement, consider:
- What concrete failure mode would directly violate it?
- What implementation anti-pattern would compromise it?
- What known industry / domain pitfall applies to a solution of this shape?
- What edge case or adversarial input would expose a weakness?

Output format: a numbered list of anti-requirements. Each item should be:
- A specific failure pattern (not a general "be good" statement).
- Phrased as the pattern itself, not as a forbidding rule
  (e.g., "hardcoded credentials in source" — not "don't hardcode credentials").
- Accompanied by a brief consequence ("→ credential leakage on first push",
  "→ silent data corruption past 10k rows").

Be precise and exhaustive within the scope of the requirements above.
Aim for 5–15 anti-requirements. Quality over quantity.
Do NOT invent failures unrelated to the requirements above.
